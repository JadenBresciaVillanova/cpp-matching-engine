Data & P&L Explained ⚠ not real profit

● Data Source: Synthetic Random

Orders are generated randomly in your browser using JavaScript — no external data, no network calls. A random number generator picks each operation (new order, cancel, or aggressive cross) using the Speed, Aggression%, and Cancel% sliders. A sine-wave function biases buy/sell probability over time, creating oscillating price waves. The mid price starts at 1000 ticks and drifts with order flow.

ⓘ How P&L Is Calculated

P&L = cash + position × mid_price
On each trade the engine executes: Buy fill → cash decreases by price × qty, position increases. Sell fill → cash increases by price × qty, position decreases. The “mid_price” term marks your open position to the current market midpoint. When you hold inventory against the price trend, this mark-to-market goes negative — that’s inventory risk, the same thing real market-makers manage.

⚙ What the Engine Does

Each generated operation is fed to the selected book model (Optimized, Tree, etc.). The engine adds the order to the book, checks if it crosses the best price on the other side, and executes any resulting trades — exactly as a real exchange would. The only difference: latency is measured in JavaScript microseconds here; the C++ engine achieves nanoseconds.

✗ Why This Is Not Real Profit

This engine is simultaneously the buyer, the seller, and the exchange. Every sell order it generates has a matching buy from the same system. In a real market:

  • You are only on one side. You post a bid or an ask — someone else fills the other side. Here, both sides are the engine.
  • Adverse selection. In real markets, the people filling your orders often know something you don’t. The engine has no information advantage over itself.
  • Market impact. Large orders move the price. The engine’s synthetic orders don’t affect any real market.
  • Fees, slippage, queue position. Real exchanges charge per-trade fees. Your order may sit behind thousands of others at the same price. None of that exists here.
  • The sine-wave is deterministic. The synthetic price trend follows a predictable pattern. Real markets are driven by news, sentiment, and other participants’ strategies.

Units: P&L is in abstract tick units (mid starts at 1000). These are not dollars.

This Engine vs. Production

An honest assessment of what this matching engine shares with production exchange infrastructure and what a real system requires on top. The core matching logic follows the same patterns used in production exchange software; the surrounding infrastructure is where the gap lives.

✓ What This Engine Gets Right Shared with production

✓

Direct-Indexed O(1) Price Levels

Array indexed by tick, not a tree or hash map. O(1) access, contiguous memory, cache-friendly inward walk during matching. This is the data structure choice real exchanges make for single-instrument books.

✓

Pool Allocator — Zero Malloc on Hot Path

All order slots pre-allocated. Intrusive free list hands out slots by index in O(1). A general-purpose allocator can lock, page-fault, or fragment — exactly the tail-latency spikes the design exists to eliminate.

✓

Intrusive Doubly-Linked FIFO per Level

Links live inside the Order record in the pool. O(1) append (time priority), O(1) pop on fill, O(1) cancel given a handle. No separate list-node allocation.

✓

BBO Caching with Inward Reprice

Best bid/ask cached and updated on every operation. Only scans inward when the top level empties. Avoids O(n) scan on every query.

✓

Price-Time Priority Matching

Standard exchange priority: best price first, then FIFO at each level. Partial fills on both sides, multi-level sweeps, limit-price cap, price improvement (executes at resting price).

✓

SPSC Lock-Free Ring Buffer

Single-producer/single-consumer queue connects ingest to the matching core without a mutex. Acquire/release atomics only — not even sequential consistency. Power-of-2 capacity for bitwise modular indexing.

✓

rdtscp Cycle-Accurate Timing

Not std::chrono (can alias to system_clock, non-monotonic). rdtscp returns core ID so cross-core migration samples are detected and discarded. TSC→ns calibrated once at startup.

✓

Integer Tick Prices

No floating point. Floats can't exactly represent decimal money and break the equality comparisons matching depends on. Price is a signed tick index; Quantity is unsigned.

◉ Partially Addressed Demo-level implementation

◉

Self-Trade Prevention

Cancel-incoming (cancel-aggressor) policy is implemented with OwnerId. Production systems typically support multiple STP policies (cancel-oldest, cancel-both, decrement-and-cancel) configurable per participant.

Why it matters: Firms use different STP strategies; exchanges must support all of them.
◉

Order Types

Limit, Market, IOC, FOK, and Modify are implemented. Missing: Stop/Stop-Limit, Iceberg/Reserve, Post-Only, Pegged orders, and auction order types (MOO/MOC/LOO/LOC).

Why it matters: Each order type has specific exchange rules and edge cases that affect matching semantics.
◉

Benchmarking

Per-operation percentile distributions with warmup discarded. But numbers are only meaningful on isolated bare-metal cores (isolcpus, taskset, governor=performance). VM/cloud numbers measure the hypervisor, not the engine.

Why it matters: The README honestly says "tbd" — fake numbers are worse than no numbers.
◉

Reference-Model Cross-Check

A deliberately slow std::map/deque book runs alongside the fast one on 1M+ random operations. Compares every observable. Has a shrinker. But this is fuzz testing, not formal verification.

Why it matters: Exchanges use formal methods and multi-day soak tests; fuzz is a good start, not sufficient.

✗ The Production Gap Required for a real exchange

Network & I/O

✗

Kernel Bypass (DPDK / Solarflare ef_vi / Mellanox VMA)

Production systems bypass the OS network stack entirely. The kernel adds 5–50µs of latency per packet — often larger than the matching itself. ef_vi/DPDK deliver packets directly to userspace via DMA.

✗

Hardware Timestamping & PTP Sync

NIC-level nanosecond timestamps via PTP (IEEE 1588). Software timestamps have µs-level jitter from kernel scheduling. Regulatory audit trails require NIC timestamps.

✗

Binary Wire Protocols (FIX/ITCH/OUCH)

No text parsing on the hot path. ITCH (market data out) and OUCH (order entry in) are fixed-width binary. FIX is tag-value but exchanges use pre-parsed binary variants (FIXT/SBE).

Persistence & Recovery

✗

Write-Ahead Log (WAL)

Every accepted order/cancel must be durably logged BEFORE the ack is sent. On crash, replay the WAL to reconstruct exact book state. Without this, orders are lost on restart.

✗

Deterministic Replay & Hot Standby

A secondary engine replays the same message stream to maintain identical state. On primary failure, the standby takes over with zero message loss. Requires bit-exact determinism.

Risk & Safety

✗

Pre-Trade Risk Checks

Fat-finger protection (price/size reasonability), position limits, credit checks, rate limiting. These run BEFORE matching and must not add more than ~100ns. Often in FPGA.

✗

Circuit Breakers & Kill Switches

Automatic halt when price moves exceed thresholds (LULD — Limit Up/Limit Down bands). Per-firm and market-wide kill switches. Regulatory requirement after the 2010 Flash Crash.

Regulatory & Compliance

✗

Audit Trail (CAT / MiFID II)

Every order lifecycle event timestamped to nanosecond precision, stored immutably, reported to regulators. CAT (US) requires reporting within 8AM next day. MiFID II requires 1µs timestamp granularity.

✗

Best Execution & Reg NMS

Trade-through protection: cannot execute at a price worse than the NBBO (national best bid/offer) across all venues. Requires real-time consolidated feed from all exchanges.

Hardware & OS Tuning

✗

NUMA-Aware Memory & Huge Pages

Allocate all hot data on the same NUMA node as the core. 2MB/1GB huge pages eliminate TLB misses on the pool array. Default 4KB pages cause measurable tail spikes on large books.

✗

Core Isolation & IRQ Affinity

isolcpus + taskset pins the matching thread. IRQ affinity steers all interrupts to other cores. nohz_full disables timer ticks. Without this, the kernel preempts the engine every 4ms.

Multi-Instrument & Scale

✗

Multiple Order Books

Real exchanges run thousands of instruments. Each book may live on a different core. Needs instrument lifecycle (IPO, halt, delist), symbol directory, and cross-book risk.

✗

Session Management & Client Gateway

TCP session handling, authentication, per-client rate limiting, sequence number tracking, gap recovery. The gateway is often the bottleneck, not the matching engine.

Bottom line: the matching core — the data structures, the allocation strategy, the priority logic — is the same approach used in production. The gap is the infrastructure around it: network I/O, persistence, risk, regulation, and operational tooling.

This is intentional. The core is where the computer science lives. The infrastructure is engineering plumbing that varies by exchange and jurisdiction.

Limit Order Book — The Complete Picture

A Limit Order Book (LOB) is the core data structure at the heart of every modern electronic exchange. It is the mechanism by which buyers and sellers are matched. Every stock, future, option, and cryptocurrency you trade goes through one.

Bid Side (Buyers)

Orders from participants willing to buy at a given price or lower. Sorted highest first — the best bid is the highest price anyone is willing to pay. This is the price you’d get if you market-sold right now.

Ask Side (Sellers)

Orders from participants willing to sell at a given price or higher. Sorted lowest first — the best ask is the lowest price anyone will sell at. This is the price you’d get if you market-bought right now.

Key Definitions

Limit OrderAn order to buy or sell at a specific price or better. If it can’t execute immediately, it rests in the book until someone matches against it or it’s cancelled. Most of the book’s volume is resting limit orders.
Market OrderAn order to buy or sell immediately at the best available price. It walks the opposite side of the book, consuming resting liquidity. Never rests — it either fills entirely or partially (sweeping multiple levels).
SpreadThe gap between the best bid and best ask: spread = best_ask − best_bid. A tight spread means a liquid market. The spread is the cost of immediately crossing the book.
Mid PriceThe midpoint between best bid and best ask: (bid + ask) / 2. Used as a fair-value estimate for mark-to-market calculations and analytics. Not a real tradeable price.
BBOBest Bid and Offer. The top-of-book — the single most competitive price on each side. This is what scrolling tickers show. In a fast engine, BBO must be cached for O(1) access, not recomputed each time.
Price LevelAll orders resting at the same price form a level. Within a level, orders execute in FIFO order (first-in, first-out) — this is time priority.
Price-Time PriorityThe universal matching rule: best price first, then earliest arrival first within a price. This is why the book is sorted by price and why each level is a FIFO queue.
FillWhen an incoming order matches against a resting order, both sides get a fill (partial or full). The trade executes at the resting order’s price (price improvement for the aggressor).
IOC / FOKImmediate-or-Cancel: sweep what you can, cancel the rest — never rests. Fill-or-Kill: all or nothing — if the full quantity can’t fill immediately, the entire order is rejected.
TickThe minimum price increment. Using integer ticks (not floating point) avoids the equality comparison bugs that IEEE 754 introduces. Price 100.05 at 0.01 tick size = tick index 10005.
Self-Trade PreventionPrevents a firm from accidentally matching against its own resting orders. This engine uses cancel-incoming (cancel the aggressor) when same OwnerId is detected on both sides.
DepthThe total quantity available at a given price level, or across all levels. Deep books have many resting orders; shallow books are easily swept by a single large order.

Why Latency Matters

In electronic trading, the matching engine is the bottleneck between intent and execution. Every nanosecond of matching latency is a nanosecond where:

⏱
Prices can move against you before your order is confirmed
📈
Stale orders sit in the book creating adverse selection risk
⚡
Competitors with faster engines can trade ahead of you

This is why HFT firms spend millions on custom hardware (FPGAs, kernel bypass, colocation). This project demonstrates the software-only techniques that get you 80% of the way: O(1) data structures, zero allocation, single-threaded core, cache-friendly memory layout.

How a Trade Happens (Step by Step)

1. Incoming order arrives: BUY 10 @ 1005
2. Engine checks best ask: best_ask = 1003 (price ≤ 1005, so we cross)
3. Walk the ask FIFO at 1003: resting SELL 6 @ 1003 → FILL 6 @ 1003 (resting price)
4. Remaining qty = 4. Level 1003 exhausted. Move to 1004.
5. Resting SELL 8 @ 1004: FILL 4 @ 1004 (partial fill, 4 remain resting)
6. Incoming fully filled (10/10). Two trades generated. best_ask updated to 1004.
7. If incoming had qty 20, it would keep sweeping levels until 1005 (the limit).
8. Any unfilled remainder at the limit rests as a new buy order at 1005.

What is Mechanical Sympathy?

The term comes from racing driver Jackie Stewart: “You don’t have to be an engineer to be a racing driver, but you do have to have mechanical sympathy.” In software, it means writing code that works with the hardware, not against it. A senior HFT engineer doesn’t just write correct C++ — they write code that respects cache lines, branch predictors, memory controllers, and the OS scheduler.

This page breaks down the five battles a low-latency system must fight, and how this engine fights each one.

1. The War on RAM — Memory Hierarchy & Cache Coherence

“RAM is just a really slow hard drive.” A senior engineer cares exclusively about the CPU cache (L1/L2/L3). An L1 cache hit is ~1ns. A main memory access is ~100ns — 100x slower. Every pointer chase through a tree node scattered on the heap is a cache miss.

2. The War on the OS — Eliminating Kernel Noise

In low-latency, the Operating System is the enemy. It interrupts your thread for network IRQs, timer ticks, scheduler quantum expiry, and page faults. Each interrupt costs 1-10µs — an eternity when your matching takes 100ns.

DPDK, Solarflare ef_vi, or Mellanox VMA let the NIC DMA packets directly into application memory.Documented in Production Gap as a known requirement. 3. Concurrency Without Locks — Lock-Free Programming

std::mutex is a death sentence for latency. A contested mutex hands control to the kernel (futex syscall), which may not wake you for microseconds. But bad lock-free code is even worse — a single mis-ordered atomic can corrupt your entire book.

ConceptWhat It MeansThis Engine
Memory OrderingsDefault std::atomic uses Sequential Consistency (seq_cst), which forces a heavy CPU memory barrier (MFENCE on x86). Seniors want to see acquire/release semantics — the minimum ordering that guarantees correctness.SPSC queue uses memory_order_acquire on load, memory_order_release on store. No seq_cst anywhere on the hot path.
SPSC OwnershipTrue lock-free speed comes from strict ownership. Thread A writes, Thread B reads. No multiple writers, no CAS loops, no ABA problem. The LMAX Disruptor proved this at scale.Ingest→Core→Publisher, each link is a single-writer single-reader SPSC. The matching core itself is entirely single-threaded.
False SharingIf the producer’s head_ and consumer’s tail_ share a cache line, every push/pop bounces that line between cores via the MESI protocol, adding ~40ns per operation.Head and tail are each padded to their own 64-byte cache line in the SPSC queue. No false sharing.

4. Rigorous Measurement — Proving It’s Fast

“My engine takes 500 nanoseconds on average.” — A senior engineer immediately closes the resume. Averages hide jitter. If your engine is 100ns 99% of the time but 50,000ns 1% of the time, you will lose all your money on that 1%.

PrincipleWhy It MattersThis Engine
Tail Latency (p99.9)Trading happens at the tails. A market-maker with a 100ns p50 but 10µs p99.9 will get picked off on every adverse move. Seniors only care about the distribution: p50, p99, p99.9, p99.99, max.Reports p50/p99/p99.9/max per operation type. Warmup discarded. Separate steady-state measurement.

5. Architectural Determinism

A production engine must be a deterministic state machine. Feed it the same sequence of bytes on Monday as Sunday, and it must produce the exact same state, bit-for-bit. This is what enables hot standby, replay debugging, and regulatory audit.

ConceptWhat It MeansThis Engine
The Sequencer PatternAll inputs are globally ordered before they touch the state machine. The matching core consumes a sequential stream of commands — no non-deterministic thread interleaving, no races, no undefined behavior.SPSC queue serializes all inputs into a single ordered stream. The core is single-threaded and pure-functional over its input.
Branch PredictionEvery if statement is a risk. A mispredicted branch flushes the CPU pipeline, costing 15-20 cycles (~5ns). Seniors structure hot paths to be branchless or to have highly predictable branches.[[likely]]/[[unlikely]] hints on cold paths (pool exhaustion, queue full). Hot-path matching loop has minimal branching.
Reference Cross-CheckThe only way to know if a fast, complex engine is correct is to compare it against a slow, obviously-correct reference. Run both on the same inputs, compare every output.RefOrderBook (std::map/deque) runs alongside the fast book on 1M+ random ops. Binary-search shrinker finds minimal failing prefix.

The takeaway: writing fast C++ is not about micro-optimizations. It’s about understanding how code interacts with caches, branch predictors, memory controllers, and the OS scheduler.

A senior systems engineer reading this project should recognize these patterns as industry-standard methodology.

The Full Picture: From Order Book to Trading Ecosystem

A matching engine doesn’t exist in isolation. It’s one layer in a stack that stretches from raw market data to executed trades. This page shows the complete trajectory — what this project implements, where it sits, and what surrounds it in production.

Layer 0 — Market Microstructure

Before code, there is theory. Market microstructure is the study of how exchanges work: how prices form, how liquidity providers and takers interact, why spreads exist, and what causes market impact.

Price Discovery
Prices emerge from the collision of supply and demand in the order book. The mid-price is a consensus estimate; the spread is the cost of certainty.
Adverse Selection
When someone hits your resting order, they may know something you don’t. This “informed flow” vs. “uninformed flow” distinction drives market-making economics.
Queue Priority
Your position in the FIFO queue at a price level determines whether you get filled. Faster engines place orders earlier, earning better queue position — this is where latency converts to money.

About This Engine

This is a single-threaded, allocation-free limit order book and matching engine written in C++20. It was built to demonstrate the data-structure and systems-engineering techniques that real exchange matching engines use — O(1) data structures, zero allocation, cache-friendly layout, cycle-accurate measurement.

What It Implements

  • Full price-time priority matching with multi-level sweeps
  • Limit, Market, IOC, and FOK order types
  • Modify (in-place decrease or cancel-replace)
  • Self-trade prevention (cancel-aggressor policy)
  • GTD/DAY order expiry with priority-queue scheduling
  • FIX-style lifecycle events (Ack, Fill, Cancel, Replace, Expire, Reject)
  • SPSC lock-free ring buffers for ingest and publish edges
  • LOBSTER and NASDAQ ITCH 5.0 market data parsers

Why It’s Fast

  • O(1) everything: direct-indexed array of price levels
  • Zero malloc: pool allocator with intrusive free list
  • Cache-friendly: sequential memory walk for matching
  • No locks: single-threaded core, SPSC queues at edges
  • Integer ticks: no floating-point comparison overhead
  • BBO cache: best bid/ask tracked, not recomputed
  • rdtscp timing: cycle-accurate, detects core migration
  • Branch hints: [[likely]]/[[unlikely]] on cold paths

Three Implementations

OrderBook

The fully optimized implementation. Direct-indexed array, LIFO pool, BBO cache. This is the baseline all ablation variants are measured against.

PhotonBook

Production-hardened variant. Fibonacci hash map, FIFO pool, cache-line-aligned orders, GTD expiry, FIX lifecycle events, template Sink for zero-overhead dispatch.

RefOrderBook

The reference model. std::map + std::deque — deliberately slow, obviously correct. Used as the oracle in fuzz cross-checking (1M+ random ops, every observable compared).

Test Suite

173 tests across four test binaries. The typed test suite runs the same 96 test cases against all three book implementations simultaneously. The fuzz cross-checker runs 1M+ seeded random operations and compares every observable (ExecResult fields, trade stream, BBO, open order count, bid/ask depth per tick) between the fast book and the reference model. A binary-search shrinker automatically finds the minimal failing prefix on divergence.

Honest Scope

This is a single-instrument, in-process matching engine. It does not handle: multi-instrument risk, FIX/SBE network protocol, persistence/journaling, regulatory compliance (MiFID II timestamps, audit trail), multi-venue routing, or FPGA offload. These are documented in the Production Gap tab — not because they’re missing bugs, but because the project deliberately scopes to the matching core. Adding each would be valuable; omitting them honestly is more valuable than pretending they’re not needed.

Purpose

Latency numbers are only meaningful on an isolated core of a physical Linux machine. Windows, WSL2, and VMs inject multi-microsecond jitter into the tail from context switches, hypervisor interrupts, and timer resolution — exactly the noise the engine is designed to eliminate. This page documents the results from a controlled bare-metal Linux run, including the exact environment, methodology, and step-by-step reproduction instructions.

Quick FAQ

Why Linux and not Windows?Linux exposes isolcpus, taskset, and CPU frequency governors that let you pin a process to a dedicated core with no interrupts. Windows has no equivalent — even SetThreadAffinityMask doesn’t prevent DPC/ISR delivery on the pinned core.
Why bare metal, not a VM?Hypervisors (Hyper-V, KVM) intercept rdtscp, inject VM exits, and the vCPU can be descheduled mid-measurement. A “100ns p99” measured in a VM is meaningless — the real p99 is hidden inside the hypervisor jitter.
What is isolcpus?A kernel boot parameter that removes CPUs from the scheduler. The isolated core runs nothing except what you explicitly pin to it — no kernel threads, no interrupts, no timers. This eliminates OS-induced tail latency.
What is invariant TSC?Modern x86 CPUs tick the timestamp counter at a constant rate regardless of power state or frequency scaling. We verify this at startup. If the TSC isn’t invariant, rdtscp-based timing would drift with frequency changes.
Can I reproduce this?Yes — follow the step-by-step guide below. An AWS c5.metal bare-metal instance costs ~$4.08/hr on-demand; the full run takes under 15 minutes. Total cost: ~$1. Alternatively, use any spare physical x86 Linux box for free.
