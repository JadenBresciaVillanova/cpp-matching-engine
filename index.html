The Problem: How Do Stock Exchanges Actually Work?

When you buy a share of Apple on your phone, your order doesn’t magically find a seller. It travels to a stock exchange (like NYSE or NASDAQ), where a piece of software called a matching engine pairs your buy order with someone else’s sell order. This happens for every single trade — stocks, options, futures, crypto — billions of times per day, worldwide.

The matching engine is the most performance-critical software in all of finance. At firms like Citadel Securities, Jane Street, or the NYSE itself, the difference between processing an order in 80 nanoseconds vs. 800 nanoseconds is worth millions of dollars per year. That’s the domain this project lives in.

Limit Order Book (LOB)

The data structure at the center of every exchange. It’s a sorted list of all outstanding buy orders (bids) and sell orders (asks) for a given stock. Buyers are sorted highest-price-first; sellers are sorted lowest-price-first. The gap between the best bid and best ask is called the spread.

Matching Engine

The algorithm that checks incoming orders against the book and decides: does this new order cross with an existing one? If your buy price ≥ someone’s sell price, it’s a match — a trade happens. The engine enforces price-time priority: best price wins, and if prices are equal, whoever arrived first gets filled first.

Order Types

A limit order says “buy 100 shares at $50 or less” — it rests on the book until filled. A market order says “buy 100 shares at any price” — it matches immediately. IOC (immediate or cancel) fills what it can and cancels the rest. FOK (fill or kill) is all-or-nothing. These all behave differently inside the engine.

Why Nanoseconds Matter

High-frequency trading (HFT) firms send millions of orders per second. If the engine is slow, orders queue up, prices go stale, and firms lose money on every trade. The engineering challenge is making every operation — add, cancel, match — happen in under a microsecond (1,000 nanoseconds), consistently, even under load. That’s why these engines are written in C++, not Python or Java.

What This Project Builds

A matching engine core in C++20 that applies the same data-structure and measurement techniques used in real exchange infrastructure:

O(1) price lookup — prices map directly to array indices, so finding a price level is a single memory access (no searching)
Zero allocation on the hot path — all memory is pre-allocated at startup; no malloc/new during trading, which eliminates unpredictable pauses
Intrusive linked lists — orders at each price level are chained together using pointers embedded in the order itself, so adding/removing is one pointer swap
Cached best bid/ask — the engine always knows the top of book instantly, without scanning
Lock-free message passing — orders flow in and trades flow out through SPSC ring buffers (no mutexes, no thread contention)
Cycle-accurate measurement — latency is measured by reading the CPU’s timestamp counter directly (rdtscp), with sub-nanosecond resolution

What This Doesn’t Do (On Purpose)

A real exchange is much more than a matching engine. This project deliberately focuses on the core and omits the surrounding infrastructure:

No network layer — real exchanges use specialized protocols (FIX, ITCH, OUCH) over kernel-bypass networking. This engine processes orders in-process.
Single instrument — NYSE runs thousands of stocks; this runs one. The matching logic is the same; the orchestration is different.
No crash recovery — production systems write every order to a log before acknowledging it, so they can rebuild state after a crash.
No regulation — real exchanges must timestamp every event to nanosecond precision and report to regulators (SEC, MiFID II). That’s compliance engineering, not matching.
No risk checks — production engines reject “fat finger” orders (absurd prices/sizes) before matching. Often done in hardware (FPGA).
These gaps are documented honestly in the Production Gap tab — the scope is deliberate, not accidental.

Why This Matters (The CS Problem)

The matching core — the data structures, the allocation strategy, the priority logic — is the part that requires computer science. How do you look up a price in O(1)? How do you avoid memory allocation during trading? How do you measure latency without the measurement itself adding latency? These are the problems this project solves. Everything around it (networking, persistence, compliance) is systems integration that varies by exchange and jurisdiction. System Design
Edge Architecture
Ingest Thread
Network / Parser
Ingest ThreadParses incoming market data (LOBSTER CSV or ITCH 5.0 binary) or network messages into fixed-size order structs. Runs on its own thread so parsing latency never stalls the matching core.
Supports auto-detection of format from file extension.
→
SPSC Queue
Inbound ring buffer
Inbound SPSC QueueSingle-producer single-consumer lock-free ring buffer (power-of-2 capacity, 64K slots). The ingest thread pushes, the matching core pops. No locks, no syscalls — just atomic acquire/release on cache-line-padded head/tail indices.
Zero-copy: fixed-size messages, no heap allocation.
→
Matching Core
Single pinned thread
Matching CoreThe hot path. Runs on a single CPU core pinned with taskset — no locks, no context switches, no allocations. Direct-indexed price array for O(1) lookup, pool allocator for O(1) order slots, intrusive doubly-linked FIFO per level for price-time priority.
This is where sub-microsecond latency lives.
→
SPSC Queue
Outbound ring buffer
Outbound SPSC QueueMatching core pushes trade/exec reports into this queue instead of calling callbacks that might block. Includes an overrun counter for back-pressure detection — if the publisher can't keep up, the counter increments (no data loss, just monitoring).
LMAX Disruptor pattern: fast core never waits on slow I/O.
→
Publisher Thread
Logging / Broadcast
Publisher ThreadDrains the outbound queue in batches (up to 512 per spin). Handles slow work the core must never touch: logging, network broadcast, dashboard updates. Joins cleanly on shutdown after draining remaining messages.
Decouples I/O latency from matching latency.
Tech Stack
C++20
C++20Concepts, constexpr, std::span, [[likely]]/[[unlikely]] branch hints, designated initializers. Enables zero-cost abstractions the compiler can fully inline.
 rdtscp Timing
rdtscpCPU timestamp counter instruction that also returns the core ID. Gives cycle-accurate latency measurement (~0.3ns resolution) and detects core migrations so contaminated samples are discarded. Calibrated against steady_clock at startup.
 Pool Allocator
Pool AllocatorPre-allocated slab of fixed-size order slots with an intrusive free list. O(1) allocate/deallocate, zero malloc on the hot path. Supports LIFO (cache-hot reuse) and FIFO (predictable aging) free-list policies.
 Intrusive Lists
Intrusive Doubly-Linked Listsprev/next pointers live inside the Order struct itself — no separate list-node allocation. O(1) append preserves time priority, O(1) unlink for cancel. Each price level is a FIFO queue of orders.
 SPSC Ring Buffer
SPSC Ring BufferLock-free single-producer single-consumer queue. Power-of-2 capacity with bitwise masking. Cache-line-padded head/tail to prevent false sharing. Acquire/release memory ordering — no fences, no CAS loops.
 Fibonacci Hash Map
Fibonacci Hash MapOpen-addressed hash table using Fibonacci hashing (multiply by golden ratio, shift). Linear probing with tombstone deletion. Pre-sized at 2× expected count, never grows. Replaces std::unordered_map for the order ID lookup.
 GoogleTest
GoogleTest173 typed tests covering all three book implementations (OrderBook, RefOrderBook, PhotonBook) plus a reference-model fuzz cross-check that runs 1M+ random operations and compares every observable output.
 CMake
CMakeModern target-based build with FetchContent for dependencies. Separate targets for core library, tests, benchmarks, and demos. -O3 -march=native in Release for full ISA utilization.
 LOBSTER Parser
LOBSTER ParserParses LOBSTER academic market data (CSV format with timestamp, event type, order ID, size, price, direction). Configurable tick divisor to map decimal prices to integer ticks.
 ITCH 5.0 Parser
NASDAQ ITCH 5.0Binary protocol parser for NASDAQ's Total View feed. Big-endian readers, fixed-size message types (A/F/E/C/X/D/U), symbol filtering, optional 2-byte length prefixes. Handles 20+ message types.
